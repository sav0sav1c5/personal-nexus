# Personal Nexus

A **Retrieval-Augmented Generation (RAG)** system built from scratch for learning purposes. It loads your documents (`.txt` and `.pdf`), turns them into vector embeddings, and lets you ask questions in natural language. Answers are generated by an LLM **strictly from your documents**, with source citations.

> **Version 2.0.0** — adds model caching, chat memory, PDF ingestion, two-stage retrieval with a cross-encoder reranker, RAGAS-based evaluation, and a centralized configuration system on top of the v1.0.0 core pipeline.

---

## What's new in 2.0.0

| Feature | Summary |
|---|---|
| **Model caching** | Embedding & reranker models are loaded once into memory (singleton), not on every query. |
| **Chat memory** | Multi-turn conversations with a windowed history (last 5 exchanges). |
| **PDF ingestion** | Load `.pdf` files (via `pypdf`) in addition to `.txt`. |
| **Reranker** | Two-stage retrieval: wide bi-encoder search → precise cross-encoder rerank + relevance threshold. |
| **Evaluation** | RAGAS metrics (faithfulness, answer relevancy, context precision/recall) over a golden dataset via `/eval`. |
| **Central config** | All settings live in `src/config.py` as typed dataclasses — a single source of truth. |
| **Streaming** | Answers stream token-by-token for fast perceived response. |

## How it works

```
                          User query
                              │
             ┌────────────────┴────────────────┐
             │        (indexing runs once)      │
             │  1. Load docs (.txt / .pdf)      │
             │  2. Split into chunks            │
             │  3. Embed chunks                 │
             │  4. Store vectors in ChromaDB    │
             └────────────────┬────────────────┘
                              │
        Stage 1: bi-encoder retrieval  ──►  ~20 candidate chunks
                              │
        Stage 2: cross-encoder rerank  ──►  top 3 (above threshold)
                              │
        Generator (Groq LLM, streaming)
                              │
                          Answer + [Source: file]
```

**Why two stages?** A bi-encoder (the embedding model) is fast but compares query and chunk *independently*, so "semantically close but wrong" chunks leak through. A cross-encoder reads the query and a chunk *together* and scores them jointly — far more precise, but too slow to run over the whole database. So we retrieve wide with the bi-encoder, then rerank narrow with the cross-encoder and drop anything below a relevance threshold.

## Tech stack

| Layer | Technology |
|---|---|
| Language | Python 3.11+ |
| Document loading | LangChain + `pypdf` |
| Text splitting | Custom recursive splitter |
| Embeddings | sentence-transformers `paraphrase-multilingual-MiniLM-L12-v2` (384-dim, 50+ languages incl. Serbian) |
| Vector database | ChromaDB (persistent, cosine) |

| Evaluation | RAGAS 0.4.x |
| Config / secrets | dataclasses + python-dotenv |

## Running locally

### Prerequisites
- Python 3.11+
- A free Groq API key ([console.groq.com](https://console.groq.com))

### 1. Clone and set up the environment

```bash
git clone https://github.com/sav0sav1c5/personal-nexus.git
cd personal-nexus

python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

### 2. Add your documents

Drop `.txt` and/or `.pdf` files into `data/`:

```
data/
├── python_basics.txt
├── pandas_basics.txt
├── machine_learning.txt
└── evaluation-rag.pdf
```

### 3. Configure your API key

Create a `.env` file in the project root:

```bash
GROQ_API_KEY=gsk_your_groq_api_key_here
```

### 4. Run

```bash
python src/main.py
```

The index is built automatically on the first query (or first run) and reused afterwards.

## Configuration

Everything is centralized in [`src/config.py`](src/config.py) as typed dataclasses. Change a value in one place; the whole pipeline picks it up.

| Config | Key settings | Default |
|---|---|---|
| `ChunkingConfig` | `chunk_size`, `chunk_overlap` | `800`, `150` |
| `EmbeddingConfig` | `model_name`, `device`, `normalize_embeddings` | multilingual MiniLM, `cpu`, `True` |
| `RetrievalConfig` | `n_results` | `5` |
| `RerankingConfig` | `enabled`, `n_candidates`, `n_final`, `min_rerank_score` | `True`, `20`, `3`, `0.1` |
| `LLMConfig` | `model`, `temperature`, `max_tokens` | `llama-3.1-8b-instant`, `0.15`, `512` |
| `SystemConfig` | `measure_time`, per-stage `verbose_*` flags | `True`, all `False` |

**Verbose logging** is per stage. To debug only reranking, set `verbose_reranking = True` in `SystemConfig` — no need to flood every phase.

**Disabling the reranker** (`RerankingConfig.enabled = False`) falls back to plain bi-encoder retrieval, which is useful for A/B comparing quality with `/eval`.

## Evaluation

`/eval` runs a RAGAS evaluation over a hand-written "golden" dataset of question / ground-truth pairs (`src/evaluation/eval_config.py`). For each question it runs the **same** retrieval path the app uses (retrieve + rerank), generates an answer, and scores it on:

- **Faithfulness** — is the answer grounded in the retrieved context (no hallucination)?
- **Answer relevancy** — does the answer actually address the question?
- **Context precision** — are the retrieved chunks relevant / well-ranked?
- **Context recall** — did retrieval bring back everything needed?

An LLM (Groq, temperature 0) acts as the judge. Results are printed as aggregate scores plus a per-question breakdown.

## Known limitations & future work
